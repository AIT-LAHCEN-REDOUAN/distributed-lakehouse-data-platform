\frontchapter{Abstract}
Modern organizations increasingly rely on data produced from multiple heterogeneous sources, including transactional systems, e-commerce platforms, behavioral event streams, and customer profile datasets. However, transforming these raw inputs into reliable, governed, and analytics-ready data products requires a structured data engineering platform capable of ingestion, storage, distributed processing, validation, orchestration, and monitoring.

This final year project presents the design and implementation of the \textbf{AdOptimizer Customer Data Platform}, a distributed Big Data lakehouse platform developed under the broader AdOptimizer AI program. The platform focuses on building a scalable data engineering foundation for multi-source customer data. It integrates Apache Kafka for ingestion, Hadoop HDFS for distributed storage, Apache Spark for distributed processing, Apache Iceberg and Hive Metastore for lakehouse table management, Trino for SQL exploration, dbt-Spark for transformation modeling, Great Expectations for data quality validation, Apache Airflow for orchestration, and Prometheus with Grafana for observability.

The project demonstrates an end-to-end architecture that transforms raw customer-related datasets into structured lakehouse layers and trusted analytical data products. The implemented solution emphasizes modularity, reproducibility, scalability, data quality, observability, and readiness for future analytics and machine learning use cases.

\keywordblock{Keywords}{Big Data, Data Engineering, Distributed Systems, Data Lakehouse, Apache Kafka, HDFS, Apache Spark, Apache Iceberg, Trino, dbt-Spark, Data Quality, Observability.}

\chapter*{GENERAL INTRODUCTION}
\addcontentsline{toc}{chapter}{GENERAL INTRODUCTION}
\markboth{GENERAL INTRODUCTION}{}

Modern organizations continuously generate customer-related data across heterogeneous sources: transactional systems, e-commerce platforms, marketing tools, behavioral event tracking, and operational applications. While the volume and variety of this information can enable more personalized experiences and better decision-making, it also creates a major engineering challenge: raw data arrives with different formats, update frequencies, quality levels, and semantics, which makes end-to-end analytics difficult without a structured data platform.

In many environments, customer data pipelines are implemented as a collection of scripts and manual exports. This approach does not scale when the number of sources increases, when data volume grows, or when analytics teams require frequent refreshes. The absence of standardized ingestion, versioned storage, and automated validation often leads to recurring issues such as duplicated work, inconsistent dashboards, and low trust in metrics. These problems become even more critical when downstream use cases depend on reliable data products, such as customer segmentation, churn analysis, recommendation systems, and marketing optimization.

A modern customer data platform must therefore combine multiple capabilities: it must ingest multi-format sources and event streams, store data efficiently and durably, support distributed processing, guarantee traceability and reproducibility, and provide a governance layer through consistent modeling and validation. From an engineering perspective, this leads naturally to a \textbf{lakehouse} architecture: a design that combines the scalability and flexibility of data lakes with the structure and reliability of data warehouses. In a lakehouse, raw data and curated data products coexist in a layered structure, while table formats and metadata services enforce consistency and enable reliable SQL access.

At the same time, business stakeholders expect reliable indicators that can be updated frequently and audited easily. This requires a data engineering foundation that is scalable, reproducible, and observable. In practice, such a foundation must address four core needs:
\begin{itemize}
    \item reliable ingestion of multi-source data, including event streams and batch files
    \item distributed storage with a clear organization strategy (raw, curated, analytics-ready)
    \item distributed processing and transformation with governance and data quality controls
    \item orchestration and monitoring to ensure operational reliability and traceability
\end{itemize}

This final year project presents the design and implementation of the \textbf{AdOptimizer Customer Data Platform}, a distributed Big Data lakehouse platform developed under the AdOptimizer AI initiative. The solution integrates Apache Kafka for ingestion, Hadoop HDFS for distributed storage, Apache Spark for distributed processing, Apache Iceberg and Hive Metastore for lakehouse table management, Trino for SQL query and exploration, dbt-Spark for transformation modeling, a lightweight Great Expectations-based validation step for data quality, Apache Airflow for orchestration, and Prometheus with Grafana for observability.

Beyond implementing the technical components, this project emphasizes operational engineering practices:
\begin{itemize}
    \item modularization of the platform into clear layers (ingestion, storage, processing, transformation, query, quality, orchestration, monitoring)
    \item container-based deployment for reproducibility and portability across environments
    \item idempotent reprocessing capabilities to support experimentation and debugging
    \item monitoring of service health and pipeline execution to improve reliability
\end{itemize}

The remainder of this report is organized to first introduce the project context, then establish the theoretical background, before detailing the requirements, design, implementation, validation, and deployment strategy of the proposed platform. The report concludes with a case study on multi-source customer datasets, a validation and performance evaluation chapter, and a deployment and scalability perspective.

\subsection{Emergence and Evolution of Big Data}
Historically, organizations relied on relational databases and data warehouses to store and analyze structured business data. Over time, new sources such as web logs, mobile applications, social platforms, sensors, and e-commerce ecosystems introduced much larger volumes of data with higher variety and faster update rates.

\subsection{The Five Vs of Big Data}
Big Data is commonly described through five key characteristics:
\begin{itemize}
    \item \textbf{Volume}: large datasets requiring scalable storage and parallel processing.
    \item \textbf{Velocity}: data that arrives continuously or needs frequent refresh cycles.
    \item \textbf{Variety}: heterogeneous sources and formats (tables, logs, events, files).
    \item \textbf{Veracity}: data quality challenges, inconsistencies, and incomplete records.
    \item \textbf{Value}: the need to transform raw data into trusted analytical products.
\end{itemize}

In the context of this project, variety is reflected by multi-source datasets (profiles, churn labels, transactions, and behavioral events), while veracity motivates validation and monitoring practices. Volume and velocity drive the need for distributed ingestion, storage, and processing, and value is achieved through curated staging, intermediate, and analytics models.

\paragraph{From 3Vs to 5Vs.}
Historically, the Big Data problem was first summarized through three core characteristics: \textbf{Volume}, \textbf{Velocity}, and \textbf{Variety}. These ``traditional'' Vs describe why classical single-system data management becomes insufficient: data becomes too large to store and process on one machine, arrives too fast to be handled by slow batch-only pipelines, and comes in formats that do not fit a rigid schema from the beginning.

As Big Data platforms matured, two additional Vs became essential for operational success. \textbf{Veracity} reflects that raw data is often incomplete, noisy, or inconsistent, which creates risks of incorrect decisions if quality is not continuously validated. \textbf{Value} emphasizes that storing data is not an objective by itself; the platform must transform raw sources into reusable analytical products (metrics, curated tables, and features) that deliver measurable impact.

From a lakehouse perspective, the transition from 3Vs to 5Vs explains why architecture must include not only ingestion and storage at scale, but also governance practices such as layered modeling, validation, and observability.

\paragraph{Quantifying volume and velocity.}
If a platform ingests on average $r$ records per second and each record has average size $s$ bytes, then the approximate data rate is:
\begin{equation}
    D = r \cdot s
\end{equation}
Over an ingestion horizon $T$ seconds, the approximate raw volume is $V = D \cdot T$. With a storage replication factor $k$ (or redundant copies for reliability), the stored volume becomes:
\begin{equation}
    V_{\text{stored}} = k \cdot V
\end{equation}
In practice, this motivates distributed storage and clear lifecycle management because raw data quickly grows even for moderate ingestion rates.

\paragraph{Quantifying veracity through basic quality ratios.}
A simple but useful quality indicator is the completeness ratio of a required field:
\begin{equation}
    C = \frac{n_{\text{non-null}}}{n_{\text{total}}}
\end{equation}
Such ratios can be tracked for critical identifiers (customer or visitor keys) and used to validate that datasets are usable for downstream analytics and future machine learning.

\subsection{Distributed Storage and Distributed Processing}
Distributed systems address scale and reliability by distributing responsibilities across multiple nodes. Two complementary capabilities are essential in Big Data platforms:
\begin{itemize}
    \item \textbf{distributed storage}: a system that stores large datasets across multiple machines while providing fault tolerance and parallel access.
    \item \textbf{distributed processing}: an engine that executes computations in parallel across worker nodes, enabling scalable transformations and analytics.
\end{itemize}

In practice, a modern platform often separates storage and compute. Storage is optimized for throughput and durability, while compute is optimized for parallel execution and resource scheduling. This separation is a key principle in lakehouse architectures, where multiple engines can access the same stored data.

\paragraph{Parallel speedup and scalability.}
If a workload takes time $T_1$ on one worker and $T_p$ on $p$ workers, the speedup is:
\begin{equation}
    S(p) = \frac{T_1}{T_p}
\end{equation}
Amdahl's law provides an upper bound when only a fraction $f$ of the workload can be parallelized:
\begin{equation}
    S(p) \le \frac{1}{(1-f) + \frac{f}{p}}
\end{equation}
This theoretical constraint explains why distributed platforms must reduce serial bottlenecks (for example, centralized metadata operations or heavy shuffle steps) and why careful partitioning and efficient I/O are critical for performance.

\section{Big Data Architectures}

\subsection{Traditional Data Warehouse Architecture}
A traditional data warehouse is designed for structured data and provides strong governance through schema-on-write. Data is typically extracted from operational systems, transformed into a curated schema, and then used for reporting and analytics.

This approach supports reliable business intelligence, but it can be less flexible for semi-structured sources and can become costly when the number of sources and data volume increase. It also encourages long ingestion cycles, which can be incompatible with high-velocity data needs.

From an operational standpoint, warehouses are strong when the business model is stable and the primary objective is consistent reporting. However, as the number of sources grows, maintaining strict schema-on-write pipelines can slow down onboarding of new datasets and can create bottlenecks for experimental analytics.

\subsection{Data Lake Architecture}
A data lake stores raw data in its original form, often using a distributed file system or object storage. It promotes schema-on-read: data is interpreted at query time rather than enforced at ingestion time.

The lake model improves flexibility and supports a wide range of formats. However, without governance mechanisms, lakes can become difficult to manage, leading to inconsistent datasets, weak quality guarantees, and reduced trust in analytics outputs.

In practice, the main risk is a ``data swamp'' effect: raw files accumulate without clear ownership, naming standards, validation, or curated access patterns. This is why modern architectures introduce layered zones and data quality checks even when adopting a lake model.

\subsection{Data Lakehouse Architecture}
The lakehouse architecture aims to combine the flexibility of data lakes with the reliability of data warehouses. A lakehouse typically relies on:
\begin{itemize}
    \item scalable distributed storage for raw and curated data
    \item a table format that supports transactional guarantees, schema evolution, and metadata management
    \item a catalog or metastore to enable consistent access across engines
    \item one or more query and processing engines to build and consume curated tables
\end{itemize}

This project adopts a lakehouse approach to organize customer data into clear layers while keeping the ability to scale, reprocess, and query data reliably.

The key innovation is that lakehouse tables provide warehouse-like guarantees over lake storage. In particular, snapshot-based metadata and managed schemas enable reproducible reads. This is essential for analytics and for future machine learning pipelines, where training must be repeatable and datasets must be traceable across versions.

\subsection{Lambda Architecture}
The Lambda architecture separates processing into two paths: a batch layer for accuracy and a speed layer for low latency. Results are combined in a serving layer to deliver queries that benefit from both approaches.

Lambda can be effective when real-time insights are required, but it introduces architectural complexity because it may require maintaining two different processing pipelines and ensuring consistency between them.

From a design perspective, Lambda addresses the trade-off between freshness and completeness. The speed layer delivers quick updates, while the batch layer periodically recomputes a reliable ground truth. In practice, an important engineering concern is ensuring that both layers implement consistent business logic and that reconciliation does not introduce inconsistent metrics in dashboards.

\subsection{Kappa Architecture}
The Kappa architecture promotes a single stream processing path. Batch reprocessing is performed by replaying events through the same processing pipeline. This model reduces duplication of logic and is well suited for event-driven systems.

In this project, ingestion is event-driven through Kafka, and reprocessing is enabled by reset and replay mechanisms, while raw and curated layers are rebuilt through repeatable jobs and transformations.

Kappa is especially relevant when the event log is treated as the system of record. The ability to replay events supports reproducibility and debugging. However, it requires careful operational controls such as defining replay windows, ensuring idempotent writes, and maintaining stable schemas so that historical events remain interpretable.

Figure~\ref{fig:lambda-kappa-project-mapping} shows how the platform combines event-driven ingestion (Kappa-inspired) with batch recomputation of lakehouse tables (Lambda-style in practice) to produce stable, auditable analytics outputs.

\paragraph{Data sources}
This block represents the heterogeneous inputs used in the project: batch-oriented files (CSV/Excel exports) and event datasets (interaction logs). The role of the platform is to normalize these sources into a unified ingestion flow, so downstream processing does not depend on source-specific formats.

\paragraph{Kafka topics (durable event log + offsets)}
Kafka acts as the ingestion backbone by storing produced records in topic partitions as an append-only log. Offsets represent the position of each consumer group in this log, which enables controlled progress tracking and reproducible reprocessing. This decouples producers from consumers: producers can publish continuously while multiple downstream consumers read independently.

\paragraph{HDFS bronze zone (immutable JSONL batches)}
The bronze zone is the persistent landing area for raw ingested data, stored as immutable JSONL batch files. It provides auditability (what exactly was ingested at a given time) and a stable batch interface for distributed processing. Keeping bronze immutable reduces the risk of silently changing raw history and supports repeatable table rebuilds.

\paragraph{Offset-based replay}
The dashed replay arrow indicates that ingestion can be replayed by resetting consumer offsets and re-consuming data from Kafka. Practically, this is used when parsing rules evolve, a dataset must be reloaded, or an ingestion run must be reproduced for validation. Replay is the core Kappa-inspired mechanism that supports reprocessing without changing upstream producers.

\paragraph{Spark batch jobs (distributed compute / recompute)}
Spark represents the batch compute engine that reads bronze batches and applies distributed transformations (schema normalization, flattening nested fields, type casting, and standardization). This is the project's main mechanism to build a reliable ground truth in table form. Batch recomputation also allows consistent rebuilds when data corrections or transformation logic changes.

\paragraph{Iceberg raw tables (snapshot-based state)}
Iceberg provides the managed table layer: Spark writes raw tables in a format that supports consistent snapshots, schema evolution, and efficient SQL reads. The snapshot property matters for analytics and ML: a query (or training job) can rely on a stable table state rather than a partially updated dataset.

\paragraph{dbt transformations (staging $\rightarrow$ intermediate $\rightarrow$ analytics)}
dbt structures SQL transformations as a dependency graph and materializes curated layers. Staging focuses on cleaning and standardizing fields, intermediate models implement reusable business logic and joins (e.g., customer profiles and aggregations), and analytics models expose final marts and KPIs. This separation makes transformation logic easier to maintain and test.

\paragraph{Trino serving / SQL access}
Trino is the interactive SQL layer used to query Iceberg tables for exploration and validation. It enables fast access to raw and curated datasets without exporting data to another system, and it supports the “consumption” side of the platform (analytics queries and verification queries).

\paragraph{Latency perspective}
Operationally, end-to-end latency can be summarized as:
\begin{equation}
    L_{\text{total}} = L_{\text{ingest}} + L_{\text{process}} + L_{\text{serve}}
\end{equation}

\subsubsection{Project rationale}
This hybrid interpretation matches the project requirements: event-driven ingestion enables decoupling and replay, while batch recomputation ensures consistent and auditable lakehouse tables suitable for analytics and future ML training.

\subsubsection{Comprehensive diagram explanation}
Figure~\ref{fig:kafka-architecture} illustrates the key components of Kafka that matter for building a reliable ingestion layer: producers publish records, brokers persist them into partition logs, and consumer groups read records while tracking progress through offsets.

\paragraph{Producers}
Producers are client applications that \textbf{publish records} into Kafka topics. A record contains a key (optional) and a value (payload). The key is important because it influences partitioning: for keyed messages, Kafka typically maps messages with the same key to the same partition. This property is used when ordering matters for a given entity (e.g., a customer, session, or visitor).

\paragraph{Brokers (data plane)}
Brokers are the storage and serving nodes of Kafka. They implement the \textbf{data plane}: persisting messages into partition logs and serving them to consumers. Each partition is an \textbf{append-only log}, which makes reads sequential and efficient, and allows consumers to re-read history by selecting an offset.

\paragraph{Topic partitions (P1/P2/P3) and leader/follower replicas}
Topics are split into partitions (P1, P2, P3 in the diagram). Each partition is replicated across brokers as \textbf{leader/follower replicas}. The leader handles reads and writes for the partition, while followers replicate data from the leader to provide fault tolerance. Replication also enables higher availability when a broker fails, because a follower can be elected as a new leader.

\paragraph{KRaft controllers (metadata quorum)}
The KRaft controllers manage the \textbf{control plane} of Kafka: cluster metadata such as topics, partitions, replica assignments, and leader elections. In KRaft mode, controllers form a \textbf{metadata quorum} to keep metadata consistent without ZooKeeper. In practice, this ensures the cluster can coordinate partition leadership and membership changes reliably.

\paragraph{Consumer group}
Consumers read records from topics and process them. A consumer group provides scalable consumption: partitions are assigned across the group so that \textbf{each partition is processed by at most one consumer in the group at a given time}. This enables parallel processing while preserving ordering guarantees per partition.

The effective parallelism is:
\begin{equation}
    C_{\text{effective}} = \min(P, C)
\end{equation}
where $P$ is the number of partitions and $C$ is the number of consumers in the group.

\paragraph{Offset commits and \texttt{\_\_consumer\_offsets}}
An offset is a cursor into a partition log. Offsets are committed to Kafka (stored in the internal topic \texttt{\_\_consumer\_offsets}) to persist consumer progress. This turns consumption into a measurable, auditable process: the system can know what has been processed and what remains.

\paragraph{Offset-based replay}
Replay is enabled by seeking to earlier offsets and consuming again. This is a key property for data engineering platforms because it supports reprocessing after correcting parsing rules, handling late-arriving data, or validating end-to-end reproducibility.

\subsubsection{Project rationale}
Kafka is used to standardize ingestion across heterogeneous datasets and to support repeatable reprocessing. By keeping data in topics with offsets, the platform can validate ingestion counts, replay datasets after corrections, and trigger downstream stages through explicit events rather than manual operations.

\textbf{In our project:} dataset producer scripts publish records to Kafka topics; consumer services read records, persist immutable bronze batches in HDFS, and emit downstream load events that trigger the raw table build process.

\subsubsection{Comprehensive diagram explanation}
Figure~\ref{fig:hdfs-architecture} summarizes how HDFS separates metadata management from block storage and uses replication to provide durability and fault tolerance for large datasets.

\paragraph{HDFS client}
The HDFS client represents any application that reads or writes data into HDFS (for example, ingestion consumers, Spark jobs, or administrative utilities). Clients do not directly manage metadata; instead they interact with the NameNode to resolve file operations and then stream block data to DataNodes.

\paragraph{NameNode (filesystem namespace + block metadata)}
The NameNode is the \textbf{metadata authority} of HDFS. It stores the filesystem namespace (directories, files, permissions) and maintains mappings between files and their blocks, and between blocks and the DataNodes that store them. Because it is the control point for metadata, keeping it consistent and durable is critical for the whole filesystem.

\paragraph{Checkpoint (periodic fsimage merge)}
The checkpoint component represents periodic persistence/compaction of metadata state (fsimage edits management). The goal is operational: it reduces recovery time and improves stability by regularly consolidating the filesystem image and edit logs.

\paragraph{DataNodes (block storage)}
DataNodes store the actual data blocks and serve client read/write operations. In the diagram, three DataNodes illustrate distribution across nodes. DataNodes periodically report to the NameNode so the NameNode can maintain up-to-date block location information.

\paragraph{Streaming blocks and the write pipeline}
When writing, the client first requests target DataNodes from the NameNode (block locations), then \textbf{streams blocks} to a chosen DataNode. Replication is typically implemented as a pipeline: the first DataNode forwards the block to additional DataNodes, ensuring that all replicas are written.

\paragraph{Block replication (replication factor $r$)}
Replication is the main durability mechanism: each block is stored on multiple DataNodes. If the probability of losing one replica during a time window is approximated by $p$ and the replication factor is $r$, a simplified upper bound for losing all replicas is:
\begin{equation}
    P_{\text{loss}} \approx p^{r}
\end{equation}
While simplified, this illustrates why increasing $r$ reduces the likelihood of complete data loss.

HDFS is used as the bronze landing zone to store immutable batches generated from Kafka consumption. This ensures durability, supports auditing, and provides a stable interface for downstream Spark jobs that build Iceberg raw tables.

\textbf{In our project:} HDFS stores the bronze zone as immutable JSONL batches and hosts the warehouse storage used by the lakehouse layers.

Figure~\ref{fig:spark-architecture} highlights the core Spark execution model used in distributed processing: a driver coordinates execution, a cluster manager allocates resources, and executors perform parallel work. Spark SQL provides the structured processing layer on top of that execution engine.

\paragraph{Driver (DAG Scheduler + Task Scheduler)}
The driver is the control component of a Spark application. It constructs the logical execution plan from user code (DataFrames/RDDs), builds a DAG of stages, and schedules tasks. It also tracks job progress and coordinates retries when tasks fail. Conceptually, the driver is responsible for transforming high-level transformations into low-level parallel tasks.

\paragraph{Cluster manager (Standalone / YARN / Kubernetes)}
The cluster manager allocates compute resources and launches executors. It decides where executors run and how many resources they receive (CPU/memory). Even in containerized deployments, the role remains the same: provide a stable mechanism for Spark to acquire and manage distributed execution capacity.

\paragraph{Executors (tasks + cache)}
Executors are the distributed worker processes that run tasks. They execute transformations on partitions of data, perform joins and aggregations, and can cache intermediate datasets to speed up repeated computations. Executors also perform local reads/writes to storage and participate in shuffle operations when required.

\paragraph{Shuffle exchange}
The dashed arrow indicates a shuffle: data redistribution across executors. Shuffles occur for operations like groupBy, joins, and sorting. They are powerful but expensive due to network and disk I/O; designing pipelines to minimize unnecessary shuffles improves performance and stability.

\paragraph{Spark SQL engine (parser + Catalyst + physical plan)}
Spark SQL enables structured transformations using SQL and DataFrames. It parses SQL, applies the Catalyst optimizer to produce an optimized logical plan, then generates a physical plan executed by the underlying Spark engine. This is a key bridge between “data engineering code” and “SQL modeling” in the platform.

Distributed speedup is commonly measured by:
\begin{equation}
    S(p) = \frac{T_1}{T_p}
\end{equation}
but practical speedup is bounded when only a fraction $f$ is parallelizable:
\begin{equation}
    S(p) \le \frac{1}{(1-f) + \frac{f}{p}}
\end{equation}
This motivates reducing unnecessary shuffles and optimizing I/O patterns.

\subsubsection{Project rationale}
Spark provides the distributed compute layer that transforms bronze batches into standardized Iceberg raw tables and supports scalable SQL transformations. It is also used as the execution engine behind dbt-Spark through the Thrift server interface.

\textbf{In our project:} Spark loads bronze batches into Iceberg raw tables and executes SQL transformations (directly and via dbt-Spark through Spark SQL / Thrift).

\paragraph{Reader engine (Trino reads snapshots)}

The data context is the configuration root of Great Expectations. It defines where expectation suites, checkpoints, and validation results are stored (local files, databases, or object stores). It is the entry point that makes the quality layer portable and reproducible across environments.

\paragraph{Expectation suite (rules / checks)}
Expectation suites contain reusable rules that data should satisfy (e.g., not-null constraints, value ranges, uniqueness). They encode quality requirements explicitly, so validation is not ad-hoc but standardized and repeatable.

\paragraph{Checkpoint (run definition)}
A checkpoint is an execution configuration that specifies which suite(s) to run, on which dataset/batch, and with which runtime parameters. It operationalizes data quality by defining how validations are triggered and how results are handled.

\paragraph{Validation results (JSON artifacts)}
Validation results are structured outputs of running expectations. They include success/failure status, counts of unexpected values, and metadata. Persisting these artifacts makes quality measurable over time and supports monitoring and audit requirements.

\paragraph{Reporting}
Reporting represents human-consumable summaries such as Data Docs or lightweight run summaries. In this project, reporting is implemented as lightweight artifacts and metrics so that quality outcomes can be integrated into pipeline monitoring.

\subsubsection{Project rationale}
The project integrates a lightweight Great Expectations-based validation step to confirm that raw tables are non-empty and that essential signals remain within acceptable quality ranges. This improves trust in the platform outputs and supports repeatability.

\textbf{In our project:} we apply a lightweight validation layer on raw Iceberg tables and persist summarized artifacts so data quality becomes observable and auditable as part of pipeline execution.

\subsubsection{Comprehensive diagram explanation}
Figure~\ref{fig:airflow-architecture} summarizes the Airflow components that together support reliable orchestration: the system loads workflow definitions (DAGs), schedules tasks based on dependencies, executes them on workers, and persists all operational state for monitoring and audit.

\paragraph{DAG bundle (DAG files source)}
This is the source directory containing DAG code. It defines the workflow structure (task graph), scheduling settings, retries, and the commands/functions executed by each task. In practice, it must be available to the parsing component so Airflow can detect changes and keep the orchestrated logic consistent with the project code.

\paragraph{DAG processor (parses + serializes)}
The DAG processor reads DAG Python files and produces a serialized representation of DAG structure and task metadata. This separates parsing from scheduling, which improves stability and performance when there are many DAGs or when DAG import logic is non-trivial. Serialization also enables consistent UI/API rendering without repeatedly importing Python modules.

\paragraph{Metadata DB (DAGs + runs + states)}
The metadata database is the system of record for orchestration state. It stores serialized DAGs, DAG runs, task instances, schedules, retries, and historical outcomes. Because all components read and write state through this database (directly or via the API server), it enables traceability and auditability of pipeline executions.

\paragraph{Scheduler (schedules + queues)}
The scheduler evaluates dependencies and determines which task instances are ready to run. It then transitions tasks to runnable states and coordinates dispatch according to the executor model. The scheduler continuously updates and reads state from the metadata database to ensure correct ordering and retry behavior.

\paragraph{Workers (execute tasks)}
Workers execute the actual task payloads (operators). In this project, those payloads include service readiness checks, ingestion steps, raw loading, validations, and transformation runs. Workers report outcomes (success/failure) and runtime information back to Airflow so the platform can be monitored and rerun reliably.

\paragraph{API server (UI + REST + task state API)}
The API server provides the web UI and REST endpoints used to view DAGs, trigger runs, and inspect execution state. It also provides an interface for task state updates, which is useful for scaling and for simplifying how different components interact with orchestration state.

\paragraph{Triggerer (deferred tasks)}
The triggerer supports deferrable tasks that wait for external conditions without holding a worker slot. While not always required for every workflow, it is important for efficient orchestration when sensors or long waits are used, because it keeps worker capacity available for compute-heavy tasks.

\paragraph{How this fits the project workflow}
Within this platform, Airflow acts as the execution backbone that enforces the correct order of steps (readiness checks $\rightarrow$ ingestion/loading $\rightarrow$ validation $\rightarrow$ transformations) and records every run so the pipeline is reproducible and auditable.

\subsubsection{Project rationale}
Airflow orchestrates the end-to-end execution order: readiness checks, ingestion and loading pipelines, quality validation, and dbt transformations. This makes the platform operationally reproducible and auditable.
\textbf{In our project:} Airflow orchestrates readiness checks, raw ingestion/loading pipelines, quality validations, and dbt transformation runs as reproducible DAG executions.

\subsubsection{Functional requirement breakdown}
The requirements in Table~\ref{tab:functional-requirements} translate into concrete capabilities that are essential for a customer data platform.

\paragraph{Unified ingestion (FR-1)}
The platform must accept heterogeneous sources without forcing each dataset to have its own isolated pipeline. The functional objective is to normalize ingestion into a common backbone so that downstream processing is not tightly coupled to the original file layout or extraction tool. This is especially important in customer analytics where sources often evolve (columns added, categorical values changed, naming inconsistencies) and onboarding new datasets should remain controlled and repeatable.

\paragraph{Immutable landing zone and replayability (FR-2)}
An immutable bronze layer is a practical requirement for auditability and controlled reprocessing. When transformation logic evolves, the platform should not depend on manual re-exports of original files. Instead, the ingestion history must remain accessible so that a rebuild becomes a deterministic engineering action. This requirement also prevents silent changes in raw history, which would undermine traceability.

\paragraph{Raw tables as a stable contract (FR-3)}
Downstream modeling should not be performed directly on raw files. Building raw tables establishes a stable contract: schemas are standardized, types are controlled, and consumers can rely on SQL access through engines. This reduces the operational cost of each new transformation because the base layer is predictable and reusable.

\paragraph{Layered modeling and reuse (FR-4)}
Layering is a functional requirement, not a documentation preference. It enforces separation of responsibilities: staging isolates source-specific cleaning, intermediate models host reusable integration logic, and analytics models expose final data products and KPIs. This structure improves maintainability and reduces the risk of inconsistent business logic scattered across scripts.

\paragraph{SQL access for validation and exploration (FR-5)}
Interactive SQL access is required for two reasons: validating that ingested datasets match expectations (row counts, basic distributions, join keys) and enabling iterative analytics work without exporting data. In a practical PFE context, this also allows the jury to verify results through clear SQL examples.

\paragraph{Operational data quality (FR-6)}
Data quality requirements are treated as operational controls. Even lightweight checks provide meaningful guarantees: datasets are non-empty, identifiers meet minimal completeness, and value ranges are reasonable. Persisted artifacts serve as evidence that data quality was evaluated rather than assumed.

\paragraph{Orchestration as an execution contract (FR-7)}
Pipeline execution must be repeatable and ordered. Orchestration provides explicit run history and task outcomes, which is essential for debugging and for proving that the platform can be executed in a deterministic sequence (readiness $\rightarrow$ ingestion $\rightarrow$ raw build $\rightarrow$ validation $\rightarrow$ transformations).

\paragraph{Operational metrics (FR-8)}
Metrics make the platform demonstrable. For each major run, the platform should expose basic indicators such as service readiness, execution durations, and success ratios. These indicators do not claim strict production SLAs, but they provide measurable evidence of operational control.

\paragraph{Reproducibility (NFR-1)}
Reproducibility is required at two levels: pipeline execution reproducibility (same steps, same order) and dataset reproducibility (stable snapshots that can be queried consistently). This is particularly important for future ML readiness, where training datasets must be traceable and repeatable.

\paragraph{Scalability (NFR-2)}

\subsection{Data Quality and Governance Requirements}
The platform is intended to produce datasets that are not only available, but also \textbf{trustworthy} for analytics and future ML usage. This requires explicit quality and governance expectations:
\begin{itemize}
    \item \textbf{Schema consistency:} raw and curated datasets must expose stable field names and types, with controlled schema evolution.
    \item \textbf{Completeness and uniqueness:} critical identifiers (customer keys, transaction IDs, event/session identifiers) should be measurable through simple quality ratios and uniqueness checks.
    \item \textbf{Traceability:} every curated dataset must be traceable back to raw tables and ultimately to bronze history (lineage through transformation dependencies).
    \item \textbf{Layer separation:} raw landing, cleaned staging, business logic, and analytics marts must remain distinguishable to avoid mixing responsibilities.
    \item \textbf{Version awareness:} table snapshots and run history must support reproducible reads for analytics and ML dataset construction.
\end{itemize}

\subsubsection{Minimal measurable quality indicators}
To keep validation actionable and implementable, quality requirements are expressed through simple, implementation-friendly indicators that can be computed during validation queries and stored as artifacts:
\begin{itemize}
    \item \textbf{Completeness indicator:} total rows vs non-null rows for critical fields (e.g., compare \texttt{COUNT(*)} with \texttt{COUNT(customer\_id)}).
    \item \textbf{Uniqueness indicator:} distinct identifier count vs total rows when uniqueness is expected (e.g., compare \texttt{COUNT(DISTINCT transaction\_id)} with \texttt{COUNT(*)}).
    \item \textbf{Duplicate detection:} identify keys with frequency $> 1$ and track the number of duplicates as a regression signal.
    \item \textbf{Range and domain checks:} verify that numerical metrics and categorical values remain within expected bounds and sets.
\end{itemize}
These indicators are not sufficient alone to prove correctness, but they provide a measurable baseline that quickly detects major regressions (empty loads, broken joins, duplicated events, or missing keys).

\subsection{Observability and Operational Requirements}
Operational requirements ensure the platform remains debuggable and demonstrable:
\begin{itemize}
    \item \textbf{Service readiness:} core services must expose readiness indicators so the pipeline can fail fast if prerequisites are not met.
    \item \textbf{Run traceability:} orchestration must record run state, task outcomes, and execution order.
    \item \textbf{Metrics visibility:} pipeline outcomes (success/failure counts, durations, validation outcomes) should be observable through metrics and dashboards.
    \item \textbf{Controlled reprocessing:} replay and recomputation must be intentional and auditable, not accidental.
\end{itemize}

\subsubsection{Operational KPIs for a PFE demonstration}
To make operational behavior visible during validation runs, a minimal set of KPIs is useful:
\begin{itemize}
    \item \textbf{End-to-end run duration} (per ingestion/load/transform run)
    \item \textbf{Run success ratio} over multiple executions (computed as successful runs divided by total runs, tracked per DAG or per pipeline stage)
    \item \textbf{Stage-level latency} (ingestion vs raw build vs transformations), which supports debugging by isolating bottlenecks
    \item \textbf{Validation outcome metrics} (number of checks passed/failed, unexpected counts)
\end{itemize}
These metrics provide an objective layer of evidence that the pipeline is operational and repeatable.

\subsection{Lakehouse Layering Strategy}
To prevent a ``data swamp'' effect and ensure clarity of responsibilities, the platform follows a layered lakehouse organization:
\begin{itemize}
    \item \textbf{Bronze (immutable landing):} raw ingested history stored as append-only files for audit and replay.
    \item \textbf{Raw (lakehouse tables):} standardized tabular form built from bronze, designed as the stable source for all downstream layers.
    \item \textbf{Staging:} cleaning and normalization to isolate source-specific quirks and enforce consistent field semantics.
    \item \textbf{Intermediate:} reusable integration logic (joins, aggregations, entity-level summarization).
    \item \textbf{Analytics:} consumption-ready marts and KPIs designed for reporting and future ML dataset extraction.
\end{itemize}

This strategy ensures that reprocessing remains possible: bronze preserves history, raw tables provide stable snapshots, and curated layers remain reconstructible through explicit transformation dependencies.

\subsubsection{Comprehensive architecture explanation}
Figure~\ref{fig:global-architecture} represents the target blueprint of the platform and clarifies how each technology maps to a specific responsibility.

\paragraph{Data sources}
Sources represent heterogeneous exports and event-like datasets. At this level, the platform does not assume consistent schemas, identifiers, or formats. The goal is to absorb this heterogeneity without breaking downstream logic.

\paragraph{Kafka ingestion}
Kafka standardizes ingestion as an append-only log. This decouples upstream production from downstream consumption and enables controlled replay through offsets. Conceptually, it makes the ingestion stage repeatable even when downstream logic changes.

\paragraph{HDFS bronze}
The bronze zone stores immutable batches that represent the ingestion ground truth for the platform. It enables auditing (what data was ingested) and supports raw table rebuilds without requiring the original external exports.

\paragraph{Spark compute}
Spark provides distributed transformations required to standardize datasets and load them into the raw table layer. This includes schema mapping, flattening, casting, deduplication steps when applicable, and basic normalization required for consistent SQL tables.

\paragraph{Iceberg tables and Hive Metastore}
Iceberg is the table format that provides snapshot-based consistency and schema evolution, while Hive Metastore is the shared catalog that allows Spark and Trino to discover the same tables. This combination is the core lakehouse contract: stable SQL access on top of file-based storage.

\paragraph{dbt-Spark}
dbt structures transformations into layers and a dependency graph. This converts transformation logic into a maintainable engineering artifact: models have clear ownership, can be tested, and are reproducible across runs.

\paragraph{Quality checks}
Validation acts as a control point: it verifies that the data reaching the raw layer satisfies minimal expectations before being used to build curated models. Persisted artifacts serve both debugging and reporting needs.

\paragraph{Trino SQL serving}
Trino provides the consumption interface for exploration, validation queries, and demonstration. It allows fast SQL access to Iceberg tables without extracting data into another system.

\paragraph{Airflow orchestration and observability}
Airflow coordinates execution and records run history, while monitoring dashboards expose readiness and run outcomes. Together they transform a set of services into an executable and observable pipeline.

\subsection{Tool Interaction and Integration}
The design relies on a small number of integration contracts:
\begin{itemize}
    \item \textbf{Kafka $\rightarrow$ HDFS:} consumers materialize ingested records into immutable bronze batches and keep replay possible through offset control.
    \item \textbf{HDFS $\rightarrow$ Spark:} Spark reads bronze history to build standardized raw tables and to rebuild them when logic evolves.
    \item \textbf{Spark $\rightarrow$ Iceberg/Hive Metastore:} table writes commit metadata so that readers can access a consistent snapshot state.
    \item \textbf{Trino $\rightarrow$ Iceberg/Hive Metastore:} Trino reads Iceberg tables through a connector that resolves metadata and plans distributed scans.
    \item \textbf{dbt-Spark:} dbt structures SQL transformations as a DAG executed on Spark SQL, producing curated layers and tests.
    \item \textbf{Quality validation:} expectations/checks are executed on raw datasets and produce persisted artifacts that can be reviewed and monitored.
    \item \textbf{Orchestration and monitoring:} Airflow coordinates the execution order, while metrics dashboards provide an operational view of readiness and pipeline outcomes.
\end{itemize}

\subsubsection{Controlled reprocessing and idempotency principles}
Two operational principles reduce the risk of inconsistent results across runs:
\begin{itemize}
    \item \textbf{Idempotent writes:} repeating a run should not silently duplicate data. In practice, this motivates partition-aware writes, overwrite strategies where appropriate, and stable job boundaries.
    \item \textbf{Explicit replay windows:} replay is a controlled action, not a side effect. Reprocessing should be triggered intentionally and recorded through orchestration so that outputs remain auditable.
\end{itemize}
These principles are particularly relevant when the platform is extended later to support continuous ingestion and more frequent refresh cycles.

\subsection{Deployment and Distribution View}
Although the project is validated in a local environment, the design anticipates distribution into logical roles. This view is a conceptual preparation for the multi-machine strategy detailed later in Chapter VII.

This view clarifies that the platform is not a single monolithic service. It is a set of cooperating components that can be distributed by responsibility:
\begin{itemize}
    \item coordination and orchestration services that manage scheduling and metadata
    \item storage and catalog services that hold durable datasets and metadata
    \item processing and query engines that execute computation and serve SQL access
\end{itemize}
Even in local deployment, thinking in terms of roles improves clarity and prepares the platform for scalability discussions.
