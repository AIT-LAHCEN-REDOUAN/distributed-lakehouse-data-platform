\chapter{Deployment Strategy and Distributed Execution}

\section{Introduction}
This chapter explains how \projectname{} is physically deployed and how its distributed character is demonstrated in practice. The objective is not only to say that several machines are used, but to clarify why services were separated the way they were, how data and control move across the environment, and how the final deployment remains reproducible and defensible in an academic setting.

\section{Control Plane Responsibilities}
The project adopts a deployment strategy based on a clear separation between a \textbf{local control plane} and a \textbf{distributed data plane}. The control plane is hosted on the local workstation, while the heavy data services are distributed across the three Linux virtual machines.

This separation is important for two reasons. First, it prevents the virtual machines from being overloaded by orchestration and monitoring services that do not need to participate directly in distributed storage or processing. Second, it makes the architecture easier to explain: the control plane governs, observes, and triggers, while the data plane stores, computes, and exposes data services.

\section{VM-Level Service Separation}
The data plane is not deployed as three identical generic machines. Instead, the services are deliberately separated according to their coordination role or worker role.

        \hline

This service distribution supports clearer operational reasoning. VM2 concentrates the services that require a central authority or coordination function, such as Kerberos, the HDFS namespace, the shared catalog, and the query coordinator. VM1 and VM3 remain focused on horizontal extension: they add storage blocks, Spark execution resources, Kafka quorum members, and Trino worker capacity.

From an academic perspective, this separation is stronger than a pseudo-distributed demonstration in which all important services still run on the same node. Here, the deployment logic itself becomes part of the engineering contribution.

\section{Data Flow Across Machines}
The report should clearly explain the end-to-end movement of data:
\begin{itemize}
  \item source datasets to Kafka,
  \item Kafka to HDFS bronze,
  \item HDFS to Spark,
  \item Spark to Iceberg,
  \item Iceberg and Metastore to Trino,
  \item transformations and validation to final analytical exposure.
\end{itemize}

The actual machine-to-machine flow follows a layered path:
\begin{enumerate}
    \item the control plane prepares or triggers the dataset ingestion process;
    \item records are published into the three-node Kafka cluster across VM1, VM2, and VM3;
    \item consumers persist the raw batches into the HDFS bronze zone governed by the NameNode on VM2 and distributed across the DataNodes on all three VMs;
    \item Spark jobs are submitted remotely to VM2 and executed across the Spark workers available in the cluster;
    \item Spark writes structured raw Iceberg tables and registers them through Hive Metastore on VM2;
    \item Trino accesses the governed metadata and exposes SQL access through its coordinator/worker architecture;
    \item dbt-spark and Great Expectations operate on top of the distributed environment from the control plane side, without collapsing the underlying data-plane separation.
\end{enumerate}

This flow is important because it proves that the platform is not a single-machine ETL disguised as a distributed system. Data transport, persistence, metadata governance, processing, and analytical access cross different services and different machines with explicit operational boundaries between them.

\section{Distributed Processing Proof}
The strongest practical proof of distributed execution in the project comes from the Spark cluster behavior. The Spark master is hosted on VM2, but executor resources are distributed across multiple workers on VM1, VM2, and VM3. This means processing capacity is not bound to a single machine.

In operational demonstrations, the Spark master interface shows several registered workers, and applications allocate executors across the available nodes depending on the execution context. This is the key difference between a truly distributed execution environment and a local-only demonstration: processing tasks can be scheduled beyond the coordinator node itself.

The deployment also includes a Spark Thrift Server and a remote Spark submission helper on VM2. These components reinforce the distributed logic of the environment:
\begin{itemize}
    \item raw Spark jobs can be launched into the cluster from the control plane through a remote submission path;
    \item transformation-oriented SQL access can target the distributed Spark environment through the Thrift interface;
    \item execution is therefore coordinated centrally but materially carried out by multiple nodes.
\end{itemize}

VM3 may sometimes appear idle during lighter workloads, which is normal in a small academic cluster. Distributed execution does not require that all workers always consume identical resources at the same time. What matters is that the cluster is capable of allocating work across multiple nodes and that the platform is engineered to support that behavior.

\section{Operational Packaging and Deployment Bundles}
The deployment is supported by explicit operational packaging rather than undocumented manual steps. Each node has its own deployment bundle, startup logic, reset logic, and preflight checks. This is a major part of the project’s reproducibility value.

The startup order is also intentional: VM2 is started first because it hosts the coordination-heavy services, then VM1 and VM3 are started to extend the cluster, and finally the local control plane is brought up after the distributed data plane is stable. This sequence reflects a real dependency-aware deployment strategy rather than arbitrary service launching.

\section{Conclusion}
This chapter clarified that the deployment of \projectname{} is intentionally distributed at both the service level and the machine level. The local control plane supervises the environment without collapsing it into a single node, VM2 plays the role of coordination leader, and VM1 and VM3 extend storage, compute, and worker capacity. Data movement, processing, and analytical access therefore take place across explicit multi-node boundaries.

The chapter also showed that the deployment is reproducible because it is supported by bundles, reset logic, startup scripts, and preflight checks. As a result, the distributed architecture can be defended not only as a conceptual design, but as an implemented and operational deployment strategy. The next chapter focuses on the security architecture that hardens this deployment and protects its critical access paths.
