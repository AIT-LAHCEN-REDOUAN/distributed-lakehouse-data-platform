\section{Project Definition and Scope}
\subsection{Problem Statement}
Customer-related data is fragmented across operational contexts. In this project, the fragmentation is represented by campaign-response and profile data, digital behavioral and purchase-intent data, and retail transaction histories. When these sources remain isolated, customer understanding stays incomplete, reprocessing becomes difficult, analytical trust weakens, and governed datasets for downstream consumers are harder to produce.

The engineering problem is therefore broader than data storage. It requires a platform that can ingest heterogeneous sources reproducibly, preserve replayable raw artifacts, process them into governed lakehouse tables, expose trusted analytical access, validate data quality, coordinate execution, observe distributed behavior, and secure core infrastructure flows.

The project addresses the following engineering question:

\begin{quote}
How can a distributed customer-data platform reproducibly ingest heterogeneous datasets, preserve replayable raw data in distributed storage, construct governed lakehouse tables, expose trusted analytical access, automate transformation and quality controls, orchestrate and monitor end-to-end execution, and secure core service interactions across a multi-node environment?
\end{quote}

\subsection{Motivation for a Distributed Lakehouse Approach}
A distributed lakehouse architecture was selected because the project combines heterogeneous ingestion, replayable raw persistence, distributed processing, metadata governance, SQL access, controlled transformations, and data-quality verification. The lakehouse model preserves the flexibility of raw distributed storage while providing managed analytical tables that can be shared across processing and query engines.

The distributed deployment also makes service responsibilities and node collaboration explicit. Storage, computation, querying, orchestration, validation, observability, and security remain separate concerns but operate through defined interfaces. This architecture therefore addresses the engineering problem as an integrated data platform rather than as a collection of isolated scripts.

\subsection{Project Identity and Academic Positioning}
The implemented system is best characterized as a \textbf{secure distributed customer-data engineering platform}. Its academic positioning combines several complementary dimensions:

\begin{itemize}
    \item a Data Engineering platform for reproducible customer-data pipelines;
    \item a Big Data architecture using distributed storage, processing, and querying;
    \item a lakehouse implementation joining replayable raw data with governed analytical tables;
    \item a secure multi-node deployment with orchestration, quality, and observability controls;
    \item a technical foundation for future Customer 360 and AI-oriented services.
\end{itemize}

This identity reflects the system that was implemented and validated; it does not position the project as a finished machine-learning product, a business-intelligence dashboard, or a simple ETL script collection.

\subsection{Project Objectives}
The project was structured around the following objectives:

\begin{enumerate}
    \item organize heterogeneous customer datasets and establish replayable ingestion through Kafka and an HDFS bronze layer;
    \item process raw data with Spark into Iceberg tables backed by Parquet and governed through Hive Metastore;
    \item expose analytical access through Trino, structure transformations with dbt-spark, and validate data quality with Great Expectations;
    \item orchestrate the complete execution sequence through Airflow and centralize operational visibility through Prometheus, Grafana, and pipeline evidence;
    \item deploy cooperating services across a local control plane and three Linux virtual machines;
    \item protect the distributed runtime through baseline controls for service identity, browser access, transport, remote execution, and persisted data.
\end{enumerate}

\subsection{Implemented Scope and Boundaries}
The implemented scope covers the active Client~1 bundle composed of the \textit{Bank Marketing}, \textit{Online Shoppers Purchasing Intention}, and \textit{Online Retail II} datasets. Together, these sources represent campaign and profile context, digital journey and purchase-intent behavior, and transactional retail activity. This combination provides a credible multi-source basis for future Customer 360 analysis while remaining compatible with the available infrastructure.

The project does not implement downstream machine-learning modules such as dynamic segmentation, churn or lifetime-value prediction, persona generation, and recommendation engines. It delivers the distributed and secured data foundation required for those capabilities, thereby keeping the report focused on the completed engineering contribution.

\subsection{Implemented Outcomes and Academic Contribution}
The completed outcome is a reproducible end-to-end platform in which heterogeneous customer datasets are ingested, persisted, processed, transformed, queried, validated, orchestrated, monitored, and secured. It provides replayable bronze artifacts in distributed storage, governed analytical tables accessible through SQL, persisted quality evidence, repeatable workflow execution, and observable collaboration across multiple nodes.

The academic contribution lies in integrating event transport, distributed storage and computation, lakehouse table management, metadata governance, analytical access, transformation control, quality assurance, orchestration, observability, deployment, and security hardening into one consistent customer-data platform. Its originality is architectural and engineering-oriented: the work demonstrates how these concerns can be combined and operated coherently within a constrained multi-node environment.
