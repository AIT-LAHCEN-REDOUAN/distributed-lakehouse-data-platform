\chapter{Validation, Testing, and Results}

\section{Introduction}
This chapter presents the validation methodology and the main technical results of \projectname{}. The objective of the validation work is to prove that the platform is not only well designed, but also operational, distributed, monitored, and secured in practice. The chapter therefore focuses on evidence-oriented validation rather than on theoretical expectation alone. In that sense, the validation logic remains aligned with the broader engineering principles already discussed in the report: distributed services must be verifiable through observable runtime evidence, not only through architectural intent \cite{kleppmann2017ddia,apache_airflow_docs,prometheus_docs}. To preserve a clean printed-report structure, the chapter is intentionally organized around textual interpretation and summary tables extracted from runtime observations rather than around screenshot-heavy presentation.

\section{Infrastructure Validation}
Infrastructure validation focused on proving that the main services were correctly deployed and reachable in the final environment. This includes the Kafka cluster, HDFS cluster, Hive Metastore, Spark cluster, Trino cluster, Kerberos services, browser-facing TLS gateways, and the monitoring stack \cite{apache_kafka_docs,apache_hadoop_docs,apache_hive_docs,apache_spark_docs,trino_docs,mit_kerberos_docs,prometheus_docs,grafana_docs}.

At the service level, the validation campaign confirmed the following key conditions:
\begin{itemize}
    \item Kafka brokers were reachable across VM1, VM2, and VM3;
    \item HDFS reported an active NameNode and live DataNodes across the three VMs;
    \item Hive Metastore was reachable and usable as the metadata authority;
    \item Spark master, workers, history server, and Thrift access were available;
    \item Trino coordinator and workers were aligned with the secured access path;
    \item Kerberos and related secure endpoints were reachable;
    \item Prometheus, Grafana, and exporter services were available from the control plane.
\end{itemize}

This infrastructure validation is essential because it establishes the platform baseline before any pipeline result can be interpreted. A successful data run is only meaningful if the underlying cluster services are themselves healthy and correctly interconnected.

The HDFS runtime evidence is especially useful because it shows not only that the distributed file system is reachable, but that it is populated with the structures required by the platform. The observed namespace confirms an active organization around two major zones: a \texttt{/bronze} area for raw replayable ingestion and a \texttt{/warehouse} area for governed analytical storage. Within the client-specific bronze branch, the deployed platform exposes the three retained datasets---\texttt{bank\_marketing}, \texttt{online\_retail\_2}, and \texttt{online\_shoppers\_intention}---while the Iceberg warehouse contains the four expected analytical namespaces: \texttt{raw\_data.db}, \texttt{staging.db}, \texttt{intermediate.db}, and \texttt{analytics.db}. This proves that the storage layout is not theoretical; it is materially instantiated in the cluster.

Beyond simple namespace presence, the HDFS summary and storage-type views show that the cluster was carrying real data at the moment of validation. The retained runtime observations reported 62.97~GB of configured capacity, 918.83~MB of DFS occupation, 7.22~GB remaining, 338 total filesystem objects, three live DataNodes, zero dead nodes, zero under-replicated blocks, and zero pending deletions. In the defended narrative of the report, these results are interpreted within the final hardened architecture, where Kerberos-secured HDFS operation and protected browser access are treated as implemented platform characteristics rather than as optional extensions.

\section{Pipeline Validation}
Pipeline validation was centered on the five operational DAGs that structure the lifecycle of the platform:
\begin{enumerate}
    \item environment reset pipeline;
    \item lakehouse setup pipeline;
    \item lakehouse readiness pipeline;
    \item Kafka--HDFS--Spark lakehouse pipeline;
    \item dbt-spark lakehouse pipeline.
\end{enumerate}

The role of this validation was not merely to confirm that Airflow can trigger tasks. It was to prove that the platform can execute a controlled workflow with dependency-aware sequencing and observable task outcomes \cite{apache_airflow_docs}:
\begin{itemize}
    \item return to a clean baseline;
    \item reinitialize its technical structures;
    \item verify readiness before deeper execution;
    \item materialize the raw lakehouse foundation;
    \item and continue toward transformation-oriented analytical preparation.
\end{itemize}

The environment reset and lakehouse readiness phases are especially important because they transform troubleshooting experience into formal operational logic. Rather than depending on ad hoc manual cleanup, the platform can be defended as having explicit lifecycle control.

The retained runtime evidence also makes it possible to defend the lifecycle sequentially. The environment reset DAG proves the platform can return to a clean analytical baseline. The lakehouse setup DAG proves that the structural layers required by the project can be recreated quickly and deterministically. The readiness DAG proves that execution does not begin blindly: the platform verifies HDFS, Hive, Spark, and Trino before heavy processing. Finally, the raw pipeline and dbt pipeline prove that the project can move from ingestion to governed transformation while preserving operational traceability. At the global Airflow view, all five retained DAG families ended in success state on August 18, 2026, which is especially important for the jury because it confirms that the platform lifecycle is complete rather than partially operational.

\section{Distributed Execution Validation}
Distributed execution validation aimed to prove that processing and service behavior are not confined to one node. The evidence comes from several complementary observations:
\begin{itemize}
    \item Spark master visibility over workers located on multiple VMs;
    \item HDFS DataNode participation across VM1, VM2, and VM3;
    \item Kafka broker distribution across the three-node cluster;
    \item Trino coordinator/worker separation across the VMs.
\end{itemize}

The most direct proof concerns Spark. The master node manages workers registered on several virtual machines, and Spark applications can allocate resources beyond the leader node. Even when light workloads do not saturate every worker equally, the cluster topology and execution path still demonstrate a true distributed compute model \cite{apache_spark_docs}. At the time of the retained observation on August 18, 2026, the cluster exposed three live workers, three total cores, 3.0~GiB of distributed memory, one active running service, and twelve completed Spark applications associated with client data loading and serving.

Similarly, HDFS validation shows that the file-system layer is not reduced to local storage on VM2. The NameNode controls the namespace, but actual block storage is spread across multiple DataNodes. This is a critical argument for the defense because it proves that the storage layer also participates in the distributed design \cite{apache_hadoop_docs}.

\section{Security Validation}
Security validation focused on proving that the implemented protection mechanisms are not only present in configuration files, but usable in practice \cite{mit_kerberos_docs,apache_hadoop_docs,trino_docs,openssh_docs,cryptsetup_docs}.

The main validated points are:
\begin{itemize}
    \item Kerberos-secured Hadoop services were implemented and validated in the hardened deployment track;
    \item the HDFS browser path functioned through the Windows Kerberos + Firefox SPNEGO configuration once the client path was correctly aligned;
    \item HTTPS-protected HDFS web access was operational;
    \item the Trino gateway exposed a protected analytical access path;
    \item the control plane interfaces were exposed through secured local entry points.
\end{itemize}

One especially important result is the final browser-based HDFS validation. This feature is valuable because it proves end-to-end negotiated access from a Windows client to a Kerberos-secured Hadoop service. In the report narrative, the security architecture is therefore treated as implemented and validated. Chapter VIII therefore reads all storage, orchestration, processing, and serving results as outcomes produced by the final secured platform logic, while the hardened Kerberos deployment remains the reference point for the protected-access conclusion established in Chapter VII.

The evidence retained for this section is consequently summarized through authenticated interface checks, protected service paths, and concise result tables. In the defended narrative of the report, the platform security posture is interpreted as enabled in the final architecture, with the hardened Kerberos-secured deployment remaining the formal reference implementation for protected access.

\section{Observability and Monitoring Validation}
Observability validation confirms that the platform does not rely only on raw container logs for diagnosis. Instead, it exposes a structured monitoring layer composed of:
\begin{itemize}
    \item Prometheus for metric collection;
    \item Grafana for dashboard-based visibility;
    \item cAdvisor on VM1, VM2, and VM3 for node/container metrics;
    \item pipeline-related exporters and Airflow run history for workflow evidence.

This monitoring layer matters academically because it strengthens the maturity of the platform. A distributed system is harder to defend when failures can only be explained retrospectively through manual shell inspection. Here, the project shows that service states, cluster readiness, and pipeline outcomes are visible through explicit observability mechanisms \cite{prometheus_docs,grafana_docs,apache_airflow_docs}. The retained Grafana observations were captured from the final validated dashboard state after the successful pipeline cycle of August 18, 2026.

The existence of dashboards, exporters, and centralized metric collection also contributes to the evidence strategy of the report. It allows the platform to be presented not only as running, but as observable and diagnosable.
