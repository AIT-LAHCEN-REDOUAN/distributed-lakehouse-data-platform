\chapter{Technology Watch}

\section{Introduction}
Chapter 2 established the theoretical logic of distributed data platforms; this chapter moves to the technical layer by presenting the main technologies retained for the implementation of \projectname. Its objective is not to document each tool exhaustively, but to justify the final stack in a concise and readable way. The selected technologies were chosen because together they support distributed ingestion, replayable storage, scalable processing, governed analytical tables, SQL access, transformation control, quality validation, orchestration, observability, and security hardening.

\section{Selection Criteria}
\begin{itemize}
    \item \textbf{Distributed compatibility:} each component had to work in a multi-node deployment rather than in a single-machine setup only.
    \item \textbf{Academic defensibility:} retained tools had to be mature, documented, and recognizable in modern data engineering practice.
    \item \textbf{Integration coherence:} technologies had to complement one another instead of creating disconnected silos.
    \item \textbf{Operational relevance:} the final stack had to support reproducibility, service separation, observability, and security hardening.
    \item \textbf{Feasibility:} the best choice was the one that offered the strongest balance between relevance, implementation realism, and clarity of demonstration.
\end{itemize}

\begin{itemize}
    \item \textbf{HDFS:} retained as the distributed raw storage layer for bronze data persistence.
    \item \textbf{Why HDFS fits:} it supports replication, replayability, multi-node durability, and strong compatibility with distributed compute.
    \item \textbf{Iceberg:} selected for the curated analytical layer of the lakehouse.
    \item \textbf{Why Iceberg fits:} it brings stronger table semantics through schema evolution, partition-aware organization, and transactional consistency.
    \item \textbf{Hive Metastore:} used as the metadata catalog for table discovery and interpretation.
    \item \textbf{Overall value:} this combination separates raw distributed persistence from governed analytical table management.
\end{itemize}

\begin{itemize}
    \item \textbf{Spark:} selected as the distributed compute engine of the platform.
    \item \textbf{Why Spark fits:} it transforms raw data into structured analytical layers while exploiting cluster parallelism and integrating naturally with HDFS and Iceberg.
    \item \textbf{Trino:} selected as the SQL access layer for interactive analytical querying.
    \item \textbf{Why Trino fits:} it clearly separates analytical access from large-scale transformation logic.
    \item \textbf{dbt-spark:} retained for transformation governance and model organization.
    \item \textbf{Why dbt fits:} it makes transformations versioned, declarative, and easier to document.
    \item \textbf{Parquet:} kept as a supporting analytical file format because it aligns well with compression and columnar query performance.
\end{itemize}

\section{Security Technology Choices}
\begin{itemize}
    \item \textbf{Kerberos:} selected for strong service authentication inside the distributed environment.
    \item \textbf{SPNEGO:} used to extend authenticated access to secured Hadoop web interfaces.
    \item \textbf{TLS:} retained to protect data movement and sensitive service exposure across nodes.
    \item \textbf{LUKS:} used to reinforce encryption at rest on protected runtime storage.
    \item \textbf{SSH:} retained for remote submission and administration in the deployment model.
    \item \textbf{Gateway protection:} credential-controlled exposure ensures that critical services remain structured and defensible.
\end{itemize}

\section{Synthesis of the Final Stack}
\begin{itemize}
    \item Kafka controls ingestion.
    \item HDFS preserves raw distributed data.
    \item Spark performs distributed transformation.
    \item Iceberg and Hive Metastore govern the lakehouse tables.
    \item Trino exposes SQL access.
    \item dbt structures transformation logic.
    \item Great Expectations validates trust in data products.
    \item Airflow orchestrates execution.
    \item Prometheus and Grafana provide observability.
    \item Docker supports service isolation and reproducible deployment.
    \item The strength of the stack lies in its coherence, not in the number of tools.
\end{itemize}
