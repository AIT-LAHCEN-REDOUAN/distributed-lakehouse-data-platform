\chapter{Technology Watch}

\section{Introduction}
Chapter II established the conceptual foundations of distributed data platforms. This chapter moves from those foundations to the technological choices implemented in \projectname{}. Its purpose is not to reproduce product documentation or to present popular tools in isolation. It explains how the retained stack was evaluated against the project's actual constraints, which alternatives were considered, and why the selected technologies form a coherent platform.

The assessment is retrospective and implementation-based. The resulting platform is already deployed as a local control plane connected to a distributed data plane composed of three Linux virtual machines. Consequently, the selected technologies are evaluated according to their demonstrated contribution to ingestion, distributed storage, processing, lakehouse governance, analytical access, transformation, quality, orchestration, observability, deployment reproducibility, and security.

\section{Project Constraints and Selection Criteria}
The technology choices were guided by the implemented environment rather than by an abstract enterprise-scale target. The main constraints were the following:
\begin{itemize}
    \item \textbf{Distributed execution:} the core storage, processing, ingestion, and query services had to demonstrate real cooperation across VM1, VM2, and VM3.
    \item \textbf{Limited infrastructure:} the deployment had to remain operable on three resource-constrained virtual machines without dedicated accelerators.
    \item \textbf{Interoperability:} processing, table management, metadata, and query technologies had to exchange data through compatible interfaces rather than through isolated proprietary paths.
    \item \textbf{Replayability and reproducibility:} ingestion and transformation stages had to support controlled re-execution, explicit dependencies, and repeatable deployment.
    \item \textbf{Operational evidence:} the platform had to expose observable service state, workflow history, validation results, and distributed-execution evidence.
    \item \textbf{Security integration:} identity, browser access, remote submission, transport, and runtime persistence had to be protected as part of the deployed architecture.
    \item \textbf{Academic clarity:} each technology had to have a precise architectural responsibility that could be explained and defended without hiding the system behind a managed platform.
\end{itemize}

These constraints led to five principal evaluation criteria: functional suitability, distributed compatibility, cross-tool integration, operational reproducibility, and feasibility within the available infrastructure. Community maturity and documentation quality were considered supporting factors, but they were not treated as substitutes for technical fit.

\subsection{Event Ingestion and Distributed Bronze Storage}
Kafka was retained as the ingestion backbone because its partitioned-topic model maps directly to the project's dataset-specific transport and three-broker topology \cite{apache_kafka_docs}. RabbitMQ provides mature queue and stream abstractions, while Pulsar provides distributed messaging with multiple subscription models \cite{rabbitmq_docs,apache_pulsar_docs}. Both are credible alternatives, but adopting either would have introduced a different operational model without improving the required Kafka-to-HDFS replay path already implemented in the platform.

HDFS was selected for the bronze landing zone because its NameNode/DataNode architecture and configurable block replication make distributed persistence directly observable across the three VMs \cite{apache_hadoop_docs}. Local or shared folders would not demonstrate distributed storage, while object storage would provide a different access abstraction and would weaken the intended Hadoop-centered deployment demonstration. HDFS therefore serves both an engineering purpose---replayable raw persistence---and an architectural purpose by proving that bronze data is physically managed by a distributed file system.

\subsection{Lakehouse Tables, Metadata, and File Format}
Apache Iceberg manages the structured raw and curated lakehouse tables, Hive Metastore centralizes their discoverable metadata, and Parquet provides the underlying columnar file representation \cite{apache_iceberg_docs,apache_hive_docs,apache_parquet_docs}. This separation is important: Parquet defines how analytical data is stored in files, Iceberg adds table-level metadata and evolution capabilities, and Hive Metastore exposes shared catalog definitions to compatible engines.

Delta Lake and Apache Hudi were considered as alternative lakehouse table technologies \cite{delta_lake_docs,apache_hudi_docs}. Iceberg was retained because the implemented project required a neutral table layer shared by Spark and Trino, with explicit schema and partition evolution rather than a platform-specific managed environment. The choice also aligns with the report's objective of making the relationship between physical files, table metadata, and the external catalog academically visible.

\subsection{Distributed Processing, Querying, and Transformation}
Spark is the main distributed compute engine for bronze-to-raw loading and curated transformation execution. Its standalone master/worker model maps naturally to VM2 as the coordination node and VM1--VM3 as executor-bearing workers \cite{apache_spark_docs}. Apache Flink offers strong stateful processing for bounded and unbounded streams \cite{apache_flink_docs}, but the implemented workloads are primarily controlled batch and SQL transformations executed through reproducible Airflow workflows. Spark therefore provides the required distribution without introducing a second processing model that the project does not need.

Trino provides a separate distributed SQL access layer over the Iceberg and Hive-governed lakehouse \cite{trino_docs}. This separation prevents analytical exploration from being represented merely as another transformation job and gives the deployment an explicit coordinator/worker query architecture. dbt-spark then organizes staging, intermediate, and analytics transformations as declared, dependency-aware models executed against the Spark environment \cite{dbt_docs}. Using dbt-spark rather than unstructured SQL scripts makes transformation order, model ownership, and generated execution artifacts easier to inspect and reproduce.

\subsection{Quality, Orchestration, and Observability}
Great Expectations turns data quality into an explicit validation layer by applying documented expectations and persisting validation results and Data Docs evidence \cite{great_expectations_docs}. Custom validation scripts could test individual rules, but they would require the project to recreate result storage, structured suites, and human-readable evidence. The retained tool therefore supports both operational checking and the report's need for verifiable quality artifacts.

Airflow orchestrates the implemented sequence of environment reset, lakehouse setup, service readiness, the integrated Kafka--HDFS--Spark raw-loading and raw-quality stage, and dbt-spark transformation \cite{apache_airflow_docs}. Prefect and Dagster provide credible Python-oriented and asset-oriented orchestration models \cite{prefect_docs,dagster_docs}; however, Airflow's explicit DAG representation, scheduling, retries, task logs, and run history already align with the project's five-workflow execution contract.

Prometheus collects platform and exporter metrics, Grafana presents them as operational dashboards, and cAdvisor contributes container-level visibility from the VM nodes \cite{prometheus_docs,grafana_docs,cadvisor_docs}. This arrangement is more defensible than relying on isolated service logs because it provides a centralized view of infrastructure health and pipeline behavior across the control and data planes.

\subsection{Deployment Reproducibility and Security Support}
Docker packages and isolates the services deployed on the control plane and VM nodes \cite{docker_docs}. Containerization does not make the platform distributed by itself; rather, it makes the already distributed service topology repeatable by preserving explicit service definitions, configuration boundaries, and startup dependencies.

The completed platform also includes Kerberos-secured Hadoop identity, SPNEGO-protected HDFS browser access, TLS gateways, SSH-based Spark submission, and encrypted runtime storage \cite{mit_kerberos_docs,openssh_docs,cryptsetup_docs}. Their configuration and trust boundaries are analyzed in Chapter VII.

\section{Conclusion}
This technology watch justified the retained \projectname{} stack against its architectural constraints. Kafka and HDFS provide replayable ingestion and storage; Spark, Iceberg, Parquet, and Hive Metastore form the lakehouse; Trino, dbt-spark, and Great Expectations query, transform, and validate it; and Airflow, observability, Docker, and the security controls operate and protect it. Together, these choices underpin the system design formalized in Chapter IV.
